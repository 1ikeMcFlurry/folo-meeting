# TRAE-CARD BLE 广播协议（网关 / Android 手持终端）

- 版本：**v9**（2026-08-12）
- 对象：手持终端 / pad 设备开发
- 平台：**Android**（帧格式已按 Android 的广播字节预算重新设计，见 §2）

本文是**网关发送的签名 Manufacturer Data 广播的唯一对外规范**。它包含两条互不替代的定向广播协议：

- **v1 token 操作广播**：加分、扣分、失败、静默余额同步，保留对应提示音；见 §1～§10。
- **v2 档案广播**：修改 token 绝对值、token 上限、时间、昵称和本地头像名称；见 §11。
- **v3 快速档案广播（推荐）**：常用字段一包完成，昵称单独按需分片，最长轮播 4.8 秒；见 §12。

固件还识别供现场互动使用的无签名心跳前缀 `FF FF 48 42`，但它不是网关业务字段协议，
不提供定向、鉴权、去重或状态更新能力，因此不纳入本文的可发送字段清单。

小程序通过 GATT 连接修改同类信息时不使用本文，见 `doc/ble-protocol-spec.md` 的 JSON 配置协议。
`doc/ble-protocol-spec.md` 不再重复广播字段，避免网关协议与连接协议出现两份真相。

## 使用范围与字段总览（先读）

### 协议选择与基本字段

| 需求 | 协议 | Android `manufacturerId` | 完整 Manufacturer Data | 主要字段 | 设备反馈 |
|---|---|---:|---:|---|---|
| 加分、扣分、失败、余额同步、宠物开关 | v1 token 操作广播 | `0xFFFF` | 26 字节，以 `FF FF 48 42 12` 开头 | `op`、目标 SN、`seq`、`balance`、`mac` | 无空口回包；按操作刷新/播放提示音 |
| 修改 token、token 上限、时间、昵称、头像名称 | v2 档案广播 | `0x4248` | 26 字节，以 `48 42 23` 开头 | `field_id`、目标 SN、`txn_id`、分片、字段值、`mac` | 无空口回包；完整事务静默生效 |
| 5 秒内同步常用档案和昵称 | v3 快速档案广播 | `0x4248` | 每包 26 字节，以 `48 42 34/35` 开头 | 常用字段单包；昵称 11B/片、最多5片 | 无空口回包；每类事务完整后原子生效 |

三种协议共同规则：

- v1/v2 的 `target` 是目标卡 **SN（12 个十六进制字符）hex 解码后的 6 个字节**，不是扫描到的 BLE 地址，不反转；v3 为节省空间不带 `target`，通过每卡唯一 DeviceSecret 的验签结果隐式定向。
- HMAC 密钥都是该 SN 对应的 **DeviceSecret 字符串原始 ASCII 字节**，不做 hex 解码，不含结尾 NUL。
- HMAC 都覆盖完整 Manufacturer Data 的 `[0..17]`，包含 company ID，取 SHA-256 摘要前 8 字节。
- 所有多字节整数均为小端；广播无 ACK，发送完成不等于设备已经收到或应用。
- Android API 的 `payload24` 不含 company ID；本文偏移表均以卡片收到的、含 company ID 的 26 字节为准。

字段与连接 JSON 的对应关系：

| 产品字段 | v1 token 广播 | v2 `field_id` | GATT JSON（仅作语义对照） |
|---|---|---:|---|
| token 当前余额 | `balance`，u24le，范围 0..999999 | `1`，u32le，固件裁剪到 10 亿 | `token` |
| token 上限 | 不支持 | `2`，u32le，必须 ≥1 | `token_max` |
| 本地墙钟 Unix 秒 | 不支持 | `3`，u32le，必须 >0 | `time` |
| 昵称 | 不支持 | `4`，1..47 字节 UTF-8，不含 NUL | `nickname` |
| 内置头像名称 | 不支持 | `5`，1..15 字节 `[a-z0-9_-]` | `avatar_name` |
| 宠物开关/类型 | `op=0x05`，复用 `balance` | 不支持 | 无对应档案字段 |

> v1 和 v2 的 token 编码范围不同是现有协议事实：v1 为紧凑的 3 字节余额并限制到 999999；
> v2 与 GATT 档案模型一致使用 4 字节值。网关不得混用两种帧布局。

### 网关究竟可以发送什么

当前固件只接受下表中的操作和字段。**没有列出的字段一律不能通过广播发送。** 广播一次只能
发送一条 v1 操作消息，或通过一笔 v2 分片事务修改一个档案字段；v2 不支持一笔事务同时修改
多个字段。

#### v1：可发送的操作消息

v1 每条消息必须提供 `target_sn`、`op`、`seq` 和 `balance`，网关再使用该 SN 对应的
`device_secret` 生成 `mac`。

| 业务动作 | `op` | `balance` 应填写 | 工牌行为 |
|---|---:|---|---|
| 加分成功 | `0x01` | **操作完成后的 token 余额绝对值**，0..999999 | 保存并显示余额，播放加分音 |
| 扣分成功 | `0x02` | **操作完成后的 token 余额绝对值**，0..999999 | 保存并显示余额，播放扣分音 |
| 业务失败 | `0x03` | 当前实际 token 余额，0..999999 | 保存并显示余额，播放失败音 |
| 静默余额同步 | `0x04` | 后台账本中的 token 余额绝对值，0..999999 | 保存并显示余额，不播放声音 |
| 宠物关闭 | `0x05` | `0` | 关闭宠物功能，不修改 token |
| 宠物开启/选择类型 | `0x05` | `1..255`，作为宠物类型编号 | 开启宠物，不修改 token |

v1 的逻辑输入可以表示为：

```text
target_sn:    12 位十六进制 SN，例如 "f0f5bd84a86c"
device_secret:该 SN 对应的 DeviceSecret，仅用于本地计算 HMAC，不上空口
op:           0x01 / 0x02 / 0x03 / 0x04 / 0x05
seq:          0..16777215；每条新业务消息换一个值，同一消息重发保持不变
balance:      普通操作为 0..999999；op=0x05 时仅使用 0..255 表示宠物开关/类型
```

v1 **不能发送** `token_max`、时间、昵称、头像名称、音量、息屏时间、图片、音频或游戏积分。

#### v2：可发送的档案字段

v2 每笔事务必须提供 `target_sn`、`field_id`、`txn_id` 和该字段的 `value`。编码后的 value
按每片 3 字节拆分，每片分别签名并广播。

| 可发送字段 | `field_id` | 网关输入 | 空口 value 编码 | 设备校验及效果 |
|---|---:|---|---|---|
| token 当前值 | `1` | 整数 `0..1000000000` | 固定 4 字节 u32le | 保存 NVS，刷新 token 显示 |
| token 上限 | `2` | 整数 `1..1000000000` | 固定 4 字节 u32le | 必须 ≥1；保存 NVS，刷新进度上限 |
| 本地墙钟时间 | `3` | Unix 秒整数 `1..4294967295` | 固定 4 字节 u32le | 必须 >0；立即 `settimeofday`，不写 NVS |
| 昵称 | `4` | 非空 UTF-8 字符串 | UTF-8 原始字节，长度 1..47，不带 NUL | 必须为合法 UTF-8；保存 NVS，刷新昵称 |
| 内置头像名称 | `5` | 资源名称字符串 | ASCII，长度 1..15，仅 `[a-z0-9_-]` | 名称存在于设备头像包才保存并刷新 |

v2 的逻辑输入可以表示为：

```text
target_sn:     12 位十六进制 SN
device_secret: 该 SN 对应的 DeviceSecret，仅用于本地计算每片 HMAC
field_id:      1 / 2 / 3 / 4 / 5
txn_id:        0..65535；每次新的字段修改换一个值，同一事务所有分片保持不变
value:         严格按上表类型和编码生成的单个字段值
```

v2 **不能发送**宠物开关、音量、息屏时间、图片二进制、音频、乐谱、游戏积分或任意 JSON。
图片、音频、乐谱、截图等大数据只能通过 GATT 连接协议处理；头像广播只发送固件内置资源名称，
不能发送 PNG/JPEG 内容。

> 新开发的网关同步完整档案时使用 v3。v2 保留用于已部署客户端兼容和单字段诊断。

## 1. 协议在做什么

pad 对全场卡片**一对多广播**积分变动消息。每张卡从空中筛出属于自己的那条，把消息里的余额显示到屏幕上，并按指定的操作类型播提示音（加分 / 扣分 / 失败）。

两个基本前提：

- **卡片不记账。** 广播里带的是**余额绝对值**，不是增量。卡片直接赋值显示。漏收一条只是漏一次刷新，下一条自动纠正，不会永久错位。
- **同一条消息要重复发很多次**（见 §6）。卡片按**消息签名**去重，只处理第一条；
  不同 pad 发的是不同消息、签名不同，**互不干扰，无需任何跨设备协调**。

## 2. Android 字节预算（帧格式为何是现在这样）

BLE legacy 广播总容量固定 31 字节。Android 只能通过 `addManufacturerData(int, byte[])` 设置数据，无法设置原始负载，各层开销如下：

```
BLE legacy 广播总容量                        31
- Flags AD（可连接广播时系统强制添加）        3   →  28
- Manufacturer AD 头（长度 + 类型 0xFF）      2   →  26
- 公司 ID（由 manufacturerId 参数提供）       2   →  24
────────────────────────────────────────────────────
  addManufacturerData 的 byte[] 上限          24 字节
```

**本协议的 byte[] 恰好 24 字节**，加上各层开销正好 31，不多不少。

### 必须设置的广播参数

| 项 | 值 | 原因 |
|---|---|---|
| `AdvertiseSettings.setConnectable` | **false** | 卡片不会连 pad。且非连接广播时多数协议栈省略 Flags AD，能多出 3 字节余量 |
| `AdvertiseData.setIncludeDeviceName` | **false** | 设备名会额外占十几字节，必然超限 |
| `AdvertiseData.setIncludeTxPowerLevel` | **false** | 会额外占 3 字节 |
| `manufacturerId` | **0xFFFF** | BLE SIG 测试保留值，此处当魔数的一部分用 |

**如果收到 `ADVERTISE_FAILED_DATA_TOO_LARGE`，先确认上面三个开关都关了。** 若确认无误仍报错，立刻联系我们——我们还能再压缩 1~2 字节（`seq` 可降到 2 字节），但这需要卡片侧同步改，越早发现越好。

### 关于其它平台

iOS 不允许应用自定义广播的 manufacturer data，后台还会改写广播内容，**本协议在 iOS 上不可实现**。如果将来要上 iOS，需要整体换方案。

## 3. 帧格式

`addManufacturerData(0xFFFF, payload)`，其中 `payload` 为下表 `[2..25]` 共 **24 字节**。
下表偏移以**卡片收到的完整厂商数据**（含公司 ID）为基准，即 26 字节。

```
偏移      长度  内容
──────────────────────────────────────────────────────────────────
[0..1]     2   FF FF      公司 ID。由 manufacturerId=0xFFFF 提供，
                          不占 payload byte[]
──────────  以下 24 字节即 addManufacturerData 的 byte[]  ──────────
[2..3]     2   'H' 'B'    魔数，固定 0x48 0x42
[4]        1   0x12       版本与类型：高 4 位 = 版本(1)，低 4 位 = 类型(2)
                          固定填 0x12
[5]        1   op         0x01 = 加分成功
                          0x02 = 扣分成功
                          0x03 = 失败
                          0x04 = 静默同步（刷新余额，不响提示音）
                          0x05 = 宠物开关（balance=0 关闭，1..255 开启且表示宠物类型）
[6..11]    6   target     目标卡标识 —— 见 §4.1
[12..14]   3   seq        小端 uint24 —— 见 §4.2
[15..17]   3   balance    小端 uint24 —— 见 §4.3
[18..25]   8   mac        HMAC 签名 —— 见 §4.4
```

**多字节整数一律小端**（低位字节在前）。

## 4. 字段详解

### 4.1 `target`（6 字节）

**就是目标卡 SN 的原始字节。不做哈希、不做任何变换。**

SN 在台账里是 12 个十六进制字符，直接按十六进制解码成 6 字节：

```
台账里的 SN    "f0f5bd84a86c"
target 字节     F0 F5 BD 84 A8 6C
```

`target[0]` 对应 SN 字符串最左边两个字符。**不要反转字节序。**

### 4.2 `seq`（小端 uint24，范围 0 ~ 16777215）

**这个字段的语义在 v4 变了，请重读。**

它现在是一个 **nonce**，唯一作用是让"内容相同但确实是两次不同操作"的消息产生不同的签名。

| 规则 | 说明 |
|---|---|
| **每条新消息必须换一个值** | 本地递增最省事，卡片不关心具体数值 |
| 同一条消息重发时保持不变 | 卡片靠它算出的签名来去重 |
| **不需要跨设备协调** | 多台 pad 各用各的计数器，互不干扰 |
| **不需要单调、不需要持久化** | 计数器回退、重启归零都不会锁死卡片 |
| `0` 合法 | 但别一直用同一个值，否则相同内容的第二次操作会被当成重复包丢掉 |

> **v3 及更早版本要求 seq 全局单调递增，那个设计在多 pad 场景下是错的**：卡片只保留一个
> 最大值，pad A 发到 500 之后，pad B 从 1 开始发会被**全部当成重复包静默丢弃**。
> 现在卡片改为按**消息签名**去重（记住最近 16 条），该问题消失。
>
> 如果你们已经按 v3 实现了"持久化单调计数器"，**不用拆掉**——递增计数器本来就满足
> 新规则的"每条消息换个值"。只是它不再是硬性要求，回退也不会再造成故障。

### 4.3 `balance`（小端 uint24）

**变动之后的余额绝对值**，不是变动量。

- **有效范围 `0 ~ 999999`**。字段物理上限是 16777215，但**协议限定 999999**（卡片 UI 最多 6 位数），超出范围卡片整条丢弃并打警告。
- `op=0x03`（失败）时**也要填当前余额**，卡片会照常刷新显示。失败通常意味着余额没变，赋值是幂等的；万一确实变了（例如部分扣除），显示正确值比保留旧值更好。

### 4.4 `mac`（8 字节）

```
mac = HMAC-SHA256(目标卡 DeviceSecret, 厂商数据[0..17]) 的前 8 字节
```

- **签名输入 = `[0..17]` 共 18 字节**，即从公司 ID 起、到 `balance` 结束，**不含 `mac` 自身**。
- 注意签名输入**包含**公司 ID 的 `FF FF` 两字节——虽然它不在 Android 的 `byte[]` 里，计算签名时要自己补上。
- 取 HMAC-SHA256 输出的**前 8 字节**（大端顺序即摘要的自然字节序，不做反转）。

> ⚠️ **密钥编码口径**：**HMAC 密钥 = 目标卡 DeviceSecret 字符串的原始 ASCII 字节**，不做十六进制解码、不含结尾 `\0`、不做任何变换。
>
> DeviceSecret 可能看起来像十六进制串，很容易被顺手做一次 hex 解码。必须按 SN 从台账取对应
> 字符串并直接编码为 ASCII；拿错设备或做了 hex 解码都会验签失败。

## 5. 三个容易踩的坑

### 坑 1：要 SN 请读**设备名**，不要用扫描到的蓝牙地址

卡片的 BLE **设备名就是它的 SN**（12 位十六进制，如 `f0f5bd84a86c`）。扫描到的
`ScanResult.getDevice().getName()` 直接就是 SN，可以据此识别是哪张卡。

**但同一个 `ScanResult` 里的蓝牙地址不是 SN**，两者不同：

```
设备名（= SN，可直接用）      f0f5bd84a86c
蓝牙地址（≠ SN，别用）        f0:f5:bd:84:a8:6e
                                        ^^   末字节差 2
```

芯片的蓝牙 MAC = WIFI MAC 末字节 +2，而 SN 取的是 WIFI MAC。这个偏移量由芯片配置
决定，不是稳定契约。**取 SN 只有两条正确途径：读设备名，或查产线台账。**

> 注：设备名此前是固定的 `TRAE-CARD`，现已改为每台不同的 SN。如果你们有按固定名字
> 过滤设备的逻辑，需要改为按服务 UUID `54524145-4341-5244-0000-000000000000` 过滤。

### 坑 2：地址类结构体通常是反序的

即便想手工换算，注意多数 BLE API 里表示地址的字节数组是**倒着存的**（`[0]` 对应地址最右边一字节）。两个坑叠加，随手写的推导代码几乎必然是错的。

### 坑 3：长度必须精确

卡片校验"厂商数据恰好 26 字节"。多一字节少一字节都**整条静默丢弃，没有任何日志**。

Android 侧尤其注意别让系统自动追加内容（设备名、TX Power），见 §2 的开关表。

## 6. 发多久、发几次

卡片的扫描是**间歇性**的：每 160ms 开一个约 112ms 的窗口，占空比约 **70%**。这是为满足
v3 在 5 秒内收齐最多 6 种包而调整的参数；单发一次仍不可靠。

按 100ms 间隔重复广播：

| 持续时长 | 广播次数 | 整条漏收概率 |
|---|---|---|
| 1 秒 | 10 | 约 0.0006% |
| 2 秒 | 20 | 约 0.0000000003% |
| **3 秒** | **30** | **约 2×10⁻¹⁶** |

**建议每条消息持续广播 3 秒**，然后 `stopAdvertising()`。

重复 30 次不会让卡片响 30 次提示音——这 30 份内容完全一样、签名也一样，卡片只处理第一条，后续静默丢弃。这是设计预期的正常流量。

> 上表仅按 70% 扫描占空比和每次独立捕获估算，不能作为验收概率。实际结果还受广播启动/切换
> 延迟、射频碰撞、Android 厂商实现和扫描/连接并发影响；**3 秒是 v1 建议值，仍需实机测量。**

## 7. 测试向量（用于逐字节自检）

**下面用的是公开的假 DeviceSecret。** 换成目标卡真实 DeviceSecret 后签名会不同，但除 `mac` 外的所有字节应完全一致。

```
输入
  DeviceSecret "TESTPK0123456789"    （16 个 ASCII 字符，测试专用）
  SN          "f0f5bd84a86c"
  op          0x01（加分成功）
  seq         1
  balance     1234
```

```
签名输入（厂商数据 [0..17]，共 18 字节）
  ff ff 48 42 12 01 f0 f5 bd 84 a8 6c 01 00 00 d2 04 00

签名结果
  HMAC-SHA256(密钥, 上面 18 字节) 的前 8 字节
  = 19 3a 4e 54 c4 dc 27 eb
```

```
完整厂商数据（26 字节，卡片收到的内容）
  ff ff 48 42 12 01 f0 f5 bd 84 a8 6c 01 00 00 d2 04 00 19 3a 4e 54 c4 dc 27 eb

传给 addManufacturerData 的 byte[]（24 字节，去掉前 2 字节公司 ID）
  48 42 12 01 f0 f5 bd 84 a8 6c 01 00 00 d2 04 00 19 3a 4e 54 c4 dc 27 eb
```

逐字段对照：

| 偏移 | 字节 | 含义 |
|---|---|---|
| `[0..1]` | `ff ff` | 公司 ID |
| `[2..3]` | `48 42` | 魔数 `'H' 'B'` |
| `[4]` | `12` | 版本 1、类型 2 |
| `[5]` | `01` | op = 加分成功 |
| `[6..11]` | `f0 f5 bd 84 a8 6c` | target（SN 直接 hex 解码，未反转） |
| `[12..14]` | `01 00 00` | seq = 1（小端 uint24） |
| `[15..17]` | `d2 04 00` | balance = 1234（小端 uint24，0x04D2） |
| `[18..25]` | `19 3a 4e 54 c4 dc 27 eb` | mac |

**建议先用这组数据把实现跑通再接真密钥。** 如果你的输出与上面完全一致，说明字节序、字段偏移、签名范围、密钥编码四件事全对——这四项正是最容易出错、且出错后完全没有日志线索的地方。

## 8. 卡片收到之后的处理

```
① 长度 / 魔数 / 版本类型字节不对   → 静默丢弃
② target 不是自己                  → 静默丢弃（场地里 99.99% 的广播死在这一步）
③ 签名不对                         → 播失败音（3 秒内最多响一次），且整包不采信
④ balance > 999999                 → 丢弃并**打警告日志**
⑤ 该消息的签名已在最近 16 条里     → 静默丢弃（你重发的那 29 次死在这一步）
⑥ 全部通过                         → 刷新余额 + 存 flash + 按 op 播提示音
```

**③ 排在 ⑤ 之前是有意的**：签名本身就是去重的键。未经验证的签名不允许进入去重窗口，否则攻击者随便发几条伪造包就能把窗口刷满，把真实消息挤出去。

| op | 含义 | 卡片行为 |
|---|---|---|
| `0x01` | 加分成功 | **金币音**（马里奥顶金币：B5 短促 → E6 拉长，374ms），刷新余额显示 |
| `0x02` | 扣分成功 | **下坠音**（急速下行琶音 E6→C5，195ms），刷新余额显示 |
| `0x03` | 失败 | **死亡音**（马里奥死亡开头 B4-F5-停-F5-E5-C5，664ms），**同样刷新余额显示** |
| `0x04` | **静默同步** | **不响音**，只刷新余额显示 |
| `0x05` | **宠物开关** | `balance=0` 关闭 PET；`balance=1..255` 开启 PET并表示宠物类型；不修改 token。设备实现只保存低 8 位，网关不得发送 >255 |

三个音在**方向、速度、音域**三个维度上刻意错开，用户不用刻意记也能分辨：

| | 音型 | 时长 | 音域 |
|---|---|---|---|
| 加分 | 上行、拖长 | 374ms | 高（988→1320Hz）|
| 扣分 | 下行、**最快** | **195ms** | 宽跨（1320→524Hz）|
| 失败 | 先升后降、中间留白、**最慢** | **664ms** | 中低（494~698Hz）|

> 做 UI 提示时可以对上：加分是"叮～"上扬的金币声，扣分是"咻"一下坠落，失败是一小段
> 下沉的旋律。**扣分不是金币音的倒放**——那样两者音色音域完全一样，小喇叭上容易听混。

**周期性余额对账请用 `0x04`。** 用 `0x01`/`0x02` 会让工牌每次同步都叫一声——同步是后台行为，用户没做任何操作，不该有声音反馈。只有真实交易才用 `01/02/03`。

**"失败"只能由 pad 告知。** 卡片不持有账本，判断不出"余额不足"这类业务失败——库存不足、权限不够、扣分扣不动，全都要 pad 发 `op=0x03`。

## 9. 联调排查表

按这个顺序查：

| 现象 | 最可能的原因 |
|---|---|
| 卡片**完全无反应、无日志** | ① 厂商数据不是 26 字节（系统自动加了设备名 / TX Power？）② `target` 错了（是不是用了扫描到的蓝牙地址？） |
| 卡片**响失败音** | 签名对不上 → 检查是否按 SN 取了该卡 DeviceSecret、**密钥是否被误做 hex 解码**、签名范围是否为 `[0..17]` 18 字节、**签名输入是否漏了开头的 `FF FF`** |
| 相同内容的第二次操作无反应 | 新消息复用了相同 `seq`，导致整帧签名与最近消息相同；换一个 nonce 即可，重启归零本身不会锁死 |
| 卡片打警告但不响 | `balance` 超过 999999，或 `op` 不认识 |
| 偶尔漏收 | 广播时长不够，延长到 3 秒 |
| `ADVERTISE_FAILED_DATA_TOO_LARGE` | 见 §2 的三个开关 |

**排查第一步永远是：把实际发出的 26 字节抓出来，对着 §3 的表和 §7 的测试向量逐字段核对。** 绝大多数问题在这一步就能定位。

### 卡片串口会打什么日志

联调时可以让我们接一根 USB 看卡片的串口输出。**日志的信噪比是刻意设计的：静默的是常态流量，出声的一定是真问题。**

| 日志 | 含义 | 你要做什么 |
|---|---|---|
| `token 广播接收 已启用` | 开机时打印一次，说明功能就绪 | 正常。（v3 里这条还带 `last_seq=N`，v4 去掉了——不再有全局计数器） |
| `token 广播接收 已禁用(身份未完整 provision)` | 当前代码要求 DeviceSecret 与 ProductKey 均存在才启用广播接收 | 卡片侧问题，补齐身份字段；HMAC 本身只使用 DeviceSecret |
| `token 广播生效: op=N 余额=N seq=N` | **成功**，余额已刷新并落盘 | 正常 |
| `token 广播签名校验失败` | 帧到了、target 也对，**只有签名不对** | 按 SN 核对 DeviceSecret，检查是否误做 hex 解码、签名范围是否为 `[0..17]` 18 字节、**签名输入是否漏了开头的 `FF FF`** |
| `token 广播字段非法 reason=8` | `balance > 999999` | 余额超出协议范围 |
| `token 广播字段非法 reason=10` | `op` 不是 01/02/03/04/05 | 检查 op 字段 |
| **什么都不打** | 帧没到，或长度/魔数/hdr 不对，或 target 不是这张卡，或是重复包 | 抓包对字节。这几种情况卡片一律静默——场地里绝大多数广播本就与本卡无关，出声会淹没真问题 |

注意最后一行：**"完全没有日志"是最常见也最容易误判的情况**。它不代表卡片没收到，而代表包在前两级过滤（结构、目标）就被丢了。这时唯一有效的手段是抓包比对字节，猜是没用的。

## 11. v2 定向档案广播

### 11.1 用途与 Android 调用

v2 让手持终端在**不连接 GATT**的情况下修改一张卡的单个档案字段。它静默生效，不播放
加减分提示音，也不改变 v1 token 广播的任何字节。

Android 调用：

```text
addManufacturerData(0x4248, payload24)
```

`manufacturerId=0x4248` 在空口按小端形成 `48 42`，即 ASCII `HB`。`payload24` 恰好
24 字节，从下面完整厂商数据的偏移 2（`0x23`）开始。仍须关闭设备名和 TX Power，并使用
不可连接广播。

### 11.2 完整 26 字节布局

下表偏移以卡片收到的完整 Manufacturer Data 为准，其中 `[0..1]` 由 `manufacturerId`
提供，不包含在 Android 的 `payload24` 中。

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| `[0..1]` | 2 | `48 42`，company ID `0x4248` / ASCII `HB` |
| `[2]` | 1 | 版本与类型，固定 `0x23` |
| `[3]` | 1 | `field_id`，见 §11.3 |
| `[4..9]` | 6 | `target`，目标卡 SN 的 6 个原始字节，不反转 |
| `[10..11]` | 2 | `txn_id`，u16 小端；每次新的字段修改换一个值 |
| `[12]` | 1 | `fragment_index`，从 0 开始 |
| `[13]` | 1 | `fragment_count`，范围 1..16 |
| `[14]` | 1 | 完整字段值的字节数 `total_len` |
| `[15..17]` | 3 | 本片字段数据；最后一片的未用字节必须为 0 |
| `[18..25]` | 8 | HMAC-SHA256 的前 8 字节 |

多字节整数均为小端。签名计算为：

```text
mac = HMAC-SHA256(目标卡 DeviceSecret 的原始 ASCII 字节, 完整厂商数据[0..17])[:8]
```

签名输入包含开头的 `48 42`，不包含 `mac` 自身；DeviceSecret 不做 hex 解码，也不包含结尾 NUL。

### 11.3 字段定义

一次事务只能修改一个字段。

| `field_id` | 字段 | 编码与校验 | 持久化 / 显示 |
|---:|---|---|---|
| `1` | token 当前值 | 4 字节 u32 小端；设备上限裁剪为 10 亿 | 写 NVS，刷新 token 条 |
| `2` | token 上限 | 4 字节 u32 小端，必须 ≥1；设备上限裁剪为 10 亿 | 写 NVS，刷新 token 条 |
| `3` | 时间 | 4 字节 u32 小端，必须 >0；语义与连接协议一致，为本地墙钟 Unix 秒 | 立即对时，不写 NVS |
| `4` | 昵称 | 1..47 字节合法 UTF-8，不含 NUL | 写 NVS，刷新昵称 |
| `5` | 头像名称 | 1..15 字节，仅 `[a-z0-9_-]` | 名称存在才写 NVS并刷新头像 |

头像广播**不携带 PNG**。手持终端必须使用与目标设备固件同一发布包内的
`avatar_catalog.json` 生成可选名称；名称格式正确但设备资源包中不存在时，设备保留当前头像。

### 11.4 分片、事务和重发

- 每片只有 3 字节数据，`fragment_count` 必须等于 `ceil(total_len / 3)`。
- 分片可以乱序；完全相同的重复片会被接受，索引相同但内容不同会使当前事务失败。
- 活动事务由 `(field_id, txn_id)` 标识。收到另一标识时，未完成的旧事务被新事务替换。
- 相邻有效片的接收间隔达到 3000ms，设备会丢弃未完成事务；发送端切换片时不要停顿 3 秒。
- 设备记住最近 8 个已完成的 `(field_id, txn_id)`，重复发送已完成事务会被静默忽略。
- 每次真正的新修改必须换 `txn_id`；同一事务的所有分片及重发必须保持同一 `txn_id`。
- 推荐每个分片以约 100ms 间隔重复广播 3 秒，再立即切换下一片。全部片发送完后，可按相同
  `txn_id` 再重发一轮；已收到的重复片是幂等的。

设备只在所有分片收齐并完成 HMAC、字段形状、UTF-8/名称校验后原子应用该字段。target
不匹配和已完成重放静默忽略；签名或字段非法时串口最多每 3 秒打印一次
`档案广播无效,已忽略`。广播协议没有回包，手持终端不能把“发射完成”当作设备已生效确认。

### 11.5 组帧伪代码

```text
value = 字段编码后的字节串
count = ceil(len(value) / 3)
for index in 0 .. count-1:
    frame[0..1]   = 48 42
    frame[2]      = 23
    frame[3]      = field_id
    frame[4..9]   = hex_decode(SN)
    frame[10..11] = u16le(txn_id)
    frame[12]     = index
    frame[13]     = count
    frame[14]     = len(value)
    frame[15..17] = value[index*3:index*3+3]，右侧补 00
    frame[18..25] = HMAC-SHA256(DeviceSecret_ASCII, frame[0..17])[:8]
    addManufacturerData(0x4248, frame[2..25])
```

## 12. v3 快速档案广播（推荐，最长发送 4.8 秒）

### 12.1 设计目标与边界

v3 将高频、固定长度字段放入一个完整广播包；昵称使用独立包，UTF-8 长度超过 11 字节才分片。
一个最长 47 字节昵称产生 5 个昵称包，加上 1 个常用字段包，最多只有 6 种包。网关按 100ms
间隔轮播 8 轮，共 48 次发射，发送计划恰好 4.8 秒。

v3 保证的是：

- 每包独立 HMAC，损坏或伪造的包不会应用；
- 常用字段包全量校验后一次保存，不能部分生效；
- 昵称必须收齐全部分片、总长度与 UTF-8 均合法才保存；缺片保留旧昵称；
- 保存失败不提交去重键，同一 `txn_id` 的重发仍可再次尝试。

v3 仍是无连接广播，没有反向 ACK。“4.8 秒”是网关完成规定轮播的确定上限，不是无线环境下
100% 必达证明。固件扫描窗口已设为约 `112/160ms`（约 70% 占空）；按独立命中近似，最多 6 种
包、每种 8 次的理论整笔接收概率约 99.96%，真实结果必须在目标 Android 机型和现场射频环境标定。

### 12.2 定向方式与安全取舍

v3 为腾出有效载荷，不再携带 6 字节 `target`。定向身份隐含在每设备 DeviceSecret 中：网关用
目标卡密钥签名，所有卡都会看到包，但只有持有对应 DeviceSecret 的目标卡能验签通过。非目标卡
验签失败属于常态并静默忽略。

因此网关必须确保每张卡的 DeviceSecret 唯一且受控。若密钥重复，同一包会在所有共享该密钥的
卡上生效。v3 不适用于共享密钥部署。

### 12.3 常用字段包 `0x34`

Android 调用 `addManufacturerData(0x4248, frame[2..25])`。完整 Manufacturer Data：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| `[0..1]` | 2 | `48 42`，company ID `0x4248` / ASCII `HB` |
| `[2]` | 1 | 固定 `0x34` |
| `[3..4]` | 2 | `txn_id`，u16le |
| `[5]` | 1 | `field_bitmap` |
| `[6..8]` | 3 | token，u24le |
| `[9..11]` | 3 | token_max，u24le |
| `[12..15]` | 4 | 本地墙钟 Unix 秒，u32le |
| `[16]` | 1 | `avatar_id`，1-based |
| `[17]` | 1 | 保留，必须为 0 |
| `[18..25]` | 8 | `HMAC-SHA256(DeviceSecret_ASCII, frame[0..17])[:8]` |

`field_bitmap`：bit0=token、bit1=token_max、bit2=time、bit3=avatar；bit4..7 必须为 0。
未置位字段的对应字节必须全为 0。`token_max` 置位时必须 ≥1，time 置位时必须 >0，avatar
置位时 `avatar_id` 必须 ≥1。token/token_max 的 v3 范围均为 `0..16777215`，其中 token_max
不能为 0。

`avatar_id` 对应发布包 `avatar_catalog.json` 中按名称排序后的 1-based 序号：第一个头像为 1。
固件会再次按实际 AVA1 包查表；编号不存在则整包拒绝，token/time 等其它字段也不会部分应用。
网关与工牌固件必须使用同一发布包的头像目录。

示例逻辑输入：

```text
txn_id=100, token=40000, token_max=80000, time=1786500000, avatar_id=1
field_bitmap=0x0f
```

使用公开假密钥 `TESTPK0123456789` 时，上述输入的完整 26 字节 Manufacturer Data 为：

```text
48 42 34 64 00 0f 40 9c 00 80 38 01 a0 d3 7b 6a 01 00 5d b5 4f f3 b9 81 55 9b
```

### 12.4 昵称包 `0x35`

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| `[0..1]` | 2 | `48 42`，company ID `0x4248` |
| `[2]` | 1 | 固定 `0x35` |
| `[3..4]` | 2 | `txn_id`，u16le |
| `[5]` | 1 | 高4位=`fragment_count-1`，低4位=`fragment_index` |
| `[6]` | 1 | 完整昵称 UTF-8 总长度 `1..47` |
| `[7..17]` | 11 | 本片昵称字节；末片右侧必须补 0 |
| `[18..25]` | 8 | `HMAC-SHA256(DeviceSecret_ASCII, frame[0..17])[:8]` |

分片数必须严格等于 `ceil(total_len/11)`，所以实际范围为 1..5。分片可乱序，完全相同的重复片
可接受；同一索引内容冲突、元数据变化、非法补零或非法 UTF-8 会废弃当前昵称事务。片间隔达到
3 秒会清理未完成事务。收齐前绝不修改当前昵称。

同样使用 `txn_id=100`、公开假密钥 `TESTPK0123456789`，昵称 `小明` 的 UTF-8 长度为 6，单包向量为：

```text
48 42 35 64 00 00 06 e5 b0 8f e6 98 8e 00 00 00 00 00 0f ec 87 fe f3 65 25 0b
```

### 12.5 `txn_id`、原子性与去重

- 常用字段包和昵称包的去重键分别为 `(0x34, txn_id)` 与 `(0x35, txn_id)`，可使用同一批次号。
- 新的一次同步必须换 `txn_id`；同一事务的所有重复包必须保持相同内容和 ID。
- 设备分别记住最近 8 个已成功应用的事务键。
- 常用字段与昵称是两个独立的原子事务：昵称缺片不会阻止常用字段生效，反之亦然。
- 如果产品要求“常用字段和昵称必须跨两类消息一起全有或全无”，当前 v3 不提供这种跨事务原子性，
  应使用 GATT 批量配置和 DONE 确认。

### 12.6 4.8 秒轮播计划

网关先生成最多 6 个唯一包：`common, nick0, nick1, ...`，然后按原顺序轮播 8 轮，每 100ms
切换一次 Manufacturer Data：

```text
common → nick0 → ... → nickN → common → nick0 → ...
```

不要按“每一片连续广播数秒”发送。不同昵称长度的确定发送时间如下：

| 昵称 UTF-8 长度 | 昵称片数 | 加常用包后的种类 | 8轮发送时间 |
|---:|---:|---:|---:|
| 无昵称 | 0 | 1 | 0.8 秒 |
| 1..11 | 1 | 2 | 1.6 秒 |
| 12..22 | 2 | 3 | 2.4 秒 |
| 23..33 | 3 | 4 | 3.2 秒 |
| 34..44 | 4 | 5 | 4.0 秒 |
| 45..47 | 5 | 6 | 4.8 秒 |

参考实现位于 `tools/profile_broadcast_protocol.py`：`build_common()`、`build_nickname()`、
`rotation(..., rounds=8)`。这些函数返回含 company ID 的 26 字节 frame；Android API 使用
`frame[2:]` 的 24 字节 payload。
