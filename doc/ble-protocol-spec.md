## 0. 快速概览

| 项目 | 值 |
|---|---|
| 角色 | 卡片是 BLE 外设（Peripheral），小程序是中心（Central）|
| BLE 设备名 | 本机 SN（通常为 12 位小写十六进制，例如 `f0f5bd84a86c`） |
| 交互模型 | 小程序**写**命令特征下发；卡片通过**通知**回报每一步结果 |
| 数据封装 | 应用层帧 `[ver][type][len][payload]`，一帧可跨多次写 |
| 业务类型 | `0x01` 配置(JSON) / `0x02` 全屏 JPEG / `0x03` 乐谱(RTTTL) / `0x06` 屏幕截图控制 |
| 文本编码 | 全部 **UTF-8**（支持中文，一个汉字 3 字节）|
| **回应保证** | **每个动作最终必有一条「完成」或「错误」通知**（见 §3）|

## 1. GATT 特征

UUID 为 128 位，基址由 ASCII `TRAECARD` 派生，末字节区分功能。

| 名称 | UUID | 属性 | 用途 |
|---|---|---|---|
| 主服务 | `54524145-4341-5244-0000-000000000000` | — | 容器 |
| **命令写** | `54524145-4341-5244-0000-000000000010` | Write / Write Without Response | 下发配置、图片、乐谱、音频和截图控制；业务数据建议串行带响应写 |
| **状态通知** | `54524145-4341-5244-0000-000000000011` | Notify | 回报处理结果 |
| 身份只读 | `54524145-4341-5244-0000-000000000012` | Read | 读 SN/Key/硬件版本(绑定用) |
| **游戏积分只读** | `54524145-4341-5244-0000-000000000013` | Read | 读工牌本地游戏积分,见 §5「游戏积分同步」 |
| **屏幕截图通知** | `54524145-4341-5244-0000-000000000014` | Notify | 输出截图 META/DATA/END；需单独订阅 CCCD，见 §11 |

> ⚠️ 不同手机返回的 UUID 大小写可能不同；订阅/写入时**直接用 `getBLEDeviceCharacteristics` 返回的原值**。
> ⚠️ **必须订阅通知特征的 CCCD**（`notifyBLECharacteristicValueChange`），否则收不到任何回应。

### 1.1 身份只读特征 `…0012`

读取返回固定 72 字节。字符串字段使用 UTF-8/ASCII 原始字节，不带结尾 NUL，未使用空间补 0：

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| `[0]` | 1 | 版本，固定 `0x01` |
| `[1]` | 1 | flags；bit0=`1` 表示身份已 provision，判断激活状态必须看此位 |
| `[2..25]` | 24 | SN，通常为 12 个十六进制 ASCII 字符 |
| `[26..57]` | 32 | DeviceSecret/Key，供绑定流程使用，属于敏感数据 |
| `[58..65]` | 8 | 硬件版本 HwVer |
| `[66..71]` | 6 | 保留，当前为 0 |

SN 即使未 provision 也会由设备 MAC 回补，因此不能用“SN 非空”判断激活。ProductKey 不会出现在
该特征中。客户端不得记录、上传到非受控日志或公开展示 `[26..57]` 的 DeviceSecret。

## 2. 应用层帧协议

```
+--------+--------+-----------------+-------------------+
| ver(1) | type(1)|   len(2, 小端)  | payload(len 字节) |
+--------+--------+-----------------+-------------------+
  =0x01    业务类型   payload 字节数        实际数据
```

- `ver` 固定 `0x01`；`type`：`0x01`配置 / `0x02`图片 / `0x03`乐谱 / `0x05`音频片段 / `0x06`屏幕截图控制。
- `len` = payload 字节数（不含 4 字节头），**小端**。
- `payload` 上限 **256 字节**；大数据用分片子协议（§5、§6）。

### 分包规则
- 一帧可切成多个小包依次写，卡片累积重组。
- 建议连接后协商 MTU。固件按 `256 → 185 → 23` 降档主动尝试；实际值由双方协议栈决定，MTU 256 时单次 ATT 写 payload 约 253 字节。
- **必须串行、带响应写**，保证顺序。
- **一帧必须在 2 秒内写完**：相邻写包间隔超 2 秒，卡片丢弃半帧并回 `超时` 通知。

```js
async function writeFrame(type, payload /* Uint8Array */) {
  const frame = new Uint8Array(4 + payload.length);
  frame[0] = 0x01; frame[1] = type;
  frame[2] = payload.length & 0xff;
  frame[3] = (payload.length >> 8) & 0xff;
  frame.set(payload, 4);
  const step = mtu ? Math.min(mtu - 3, 240) : 20;
  for (let i = 0; i < frame.length; i += step) {
    await writeChar(frame.slice(i, i + step));   // 串行 await
  }
}
```

## 3. 通知协议（核心）

通知固定 2 字节：

```
+--------+----------+
| type(1)| status(1)|
+--------+----------+
```

### type
| 值 | 含义 |
|---|---|
| `0x00` | **帧层**问题（帧头非法/超时，判断不出业务类型）|
| `0x01` | 配置 |
| `0x02` | 图片 |
| `0x03` | 乐谱（即时播放并保存为开机音乐） |
| `0x06` | 屏幕截图控制/结果状态（像素数据不走本特征，走 `…0014`） |

### status（统一状态码）
| 值 | 名称 | 含义 | 是否终结 |
|---|---|---|---|
| `0x00` | ACK | 该帧已收到，分片传输进行中 | ❌ 进行中 |
| `0x01` | **DONE** | **整体完成**（配置已生效／图片已显示／乐谱已开始播放）| ✅ 成功 |
| `0x10` | 帧格式错 | `ver` 不是 0x01，或 `len` 非法 | ✅ 失败 |
| `0x11` | **超时** | 一帧没在 2 秒内写完，半帧已被丢弃 | ✅ 失败 |
| `0x12` | 时序错 | 未 BEGIN 就发 DATA/END，或 END 时长度对不上 | ✅ 失败 |
| `0x13` | 解析失败 | JSON / RTTTL 格式错误 | ✅ 失败 |
| `0x14` | 无有效字段 | JSON 里没有任何已知键 | ✅ 失败 |
| `0x15` | 超长 | 超过 payload 或存储上限 | ✅ 失败 |
| `0x16` | 存储失败 | flash / NVS 写入失败 | ✅ 失败 |
| `0x17` | 解码失败 | 图片尺寸不合规，或解码器在合法基线图上仍失败 | ✅ 失败 |
| `0x18` | 不支持的类型 | 未知的 type | ✅ 失败 |
| `0x19` | **图片格式不支持** | **渐进式 JPEG / 算术编码等变种。设备只支持基线 JPEG** | ✅ 失败 |
| `0x1A` | **图片数据不完整** | 缺 SOS/EOI，或根本不是 JPEG。多半是传输被截断 | ✅ 失败 |
| `0x1B` | **设备忙** | 显示正在解码/上传图片或处理截图；等待当前显示操作结束后重试 | ✅ 失败 |
| `0x1C` | **未就绪** | 截图数据 Notify 通道未连接或未订阅；重新连接并订阅 `…0014` 后重试 | ✅ 失败 |
| `0x1D` | **头像无效** | `avatar_name` 不在内置 AVA1 资源包中或资源损坏；原头像保持不变 | ✅ 失败 |

### 判定规则（小程序端只需记这一条）
> **`status == 0x00` 表示"还在进行"，其余任何值都是终结**（`0x01` 成功，`0x1X` 失败）。
> 每个动作**最终一定会收到一个终结状态**。

## 4. 各动作的完整回应时序

### 4.1 配置（type=0x01）
```
小程序                        卡片
  │──── 配置帧(1 帧) ─────────▶│
  │                            │ 解析 JSON → 存 NVS → 刷新界面
  │◀─── [01][01] DONE ─────────│  ✅ 成功
        或 [01][13] 解析失败
        或 [01][14] 无有效字段
        或 [01][16] NVS 保存失败
```
**一次下发只会收到一条通知**（终结）。

### 4.2 图片（type=0x02）
```
小程序                        卡片
  │──── BEGIN ────────────────▶│
  │◀─── [02][00] ACK ──────────│  擦除 flash 完成
  │──── DATA #1 ──────────────▶│
  │◀─── [02][00] ACK ──────────│
  │        ……(N 个 DATA)        │
  │──── END ──────────────────▶│
  │◀─── [02][00] ACK ──────────│  收齐,开始解码(耗时约 1~2 秒)
  │                            │ 解码 → 写 flash → 全屏显示
  │◀─── [02][01] DONE ─────────│  ✅ 图已显示
        或 [02][17] 解码失败      （尺寸不合规）
        或 [02][19] 格式不支持    （渐进式 JPEG ← 最常见）
        或 [02][1A] 数据不完整    （传输被截断）
        或 [02][1B] 设备忙        （上一张还在解码，等 1 秒重发）
```
`DONE` 表示全屏图已经显示。画面**不再有 6 秒自动退回**——它会常驻直到用户长按确定键退出，**退出时不发任何通知**。
⚠️ **图片有两段回应**：END 的 `ACK` 只代表"数据收齐"，**真正的终结是之后的 `DONE` 或 `0x17/0x19/0x1A` 失败**（约 1~2 秒后到达）。请等到这一条再提示用户成功。

传输中任何一步失败会立即回终结错误（`0x12` 时序错 / `0x16` 存储失败 / `0x15` 超长），此时应中止后续分片。

### 4.3 乐谱（type=0x03）

> ⚠️ **播放会被内置提示音抢占。** 卡片有几个编进固件的短提示音，触发时会**打断正在播放的乐谱**：
>
> | 触发 | 音效 | 时长 |
> |---|---|---|
> | 收到加分广播 | 金币音（马里奥顶金币） | 374ms |
> | 收到扣分广播 | 下坠音 | 195ms |
> | 收到失败广播 / 图片落盘失败 | 死亡音 | 664ms |
> | 收到心跳广播（马里奥跳跃屏） | 金币音，同上，**最快每 400ms 一次** | 374ms |
>
> 这些由**卡片自己**根据收到的广播触发，小程序无法预知也无法屏蔽。所以别把乐谱当背景音乐用——
> 它随时可能被打断且**不会自动续播**。乐谱适合做一次性的短提示或彩蛋。
```
小程序                        卡片
  │──── BEGIN ────────────────▶│
  │◀─── [03][00] ACK ──────────│
  │──── DATA #1..N ───────────▶│
  │◀─── [03][00] ACK ──────────│
  │──── END ──────────────────▶│
  │                            │ 校验 RTTTL → 唤醒播放任务
  │◀─── [03][01] DONE ─────────│  ✅ 已开始播放
        或 [03][13] RTTTL 格式错
```
乐谱的终结在 **END 时就给出**（`DONE` = 已持久化并开始播放）。

### 4.4 帧层错误（type=0x00）
| 情况 | 通知 |
|---|---|
| `ver` 不是 0x01 | `[00][10]` |
| `len` > 256 | `[00][15]` |
| **一帧没在 2 秒内写完** | `[00][11]` 超时（卡片主动检测，即使你已停止发送也会收到）|

### 4.5 未知类型
发了 `0x01/0x02/0x03/0x06` 之外的 type → `[该type][0x18]` 不支持。（`0x04` 音频流和 `0x05` 音频片段均已移除。）

### 4.6 已移除的音频类型

`type=0x04` 实时音频流与 `type=0x05` WAV/ADPCM 音频片段均已移除，设备收到后返回“不支持”。
开机、BLE 连接和游戏结束事件保持静音。用户音乐统一使用 `type=0x03` RTTTL。

## 5. 配置（type=0x01，JSON）

本节是**小程序连接蓝牙后修改设备信息**的唯一入口。手持终端不建立连接时使用的签名
广播协议见 `doc/ble-broadcast-protocol-for-gateway.md`，不要把两种帧格式混用。

payload = UTF-8 的 JSON 文本，≤256 字节。**出现哪个键改哪个字段**（部分更新），改完持久化到 NVS（掉电保留）。

| JSON 键 | 类型 | 容量 / 取值 |
|---|---|---|
| `nickname` | string | **47 字节 ≈ 15 汉字**。主页显示的昵称；推荐新客户端使用 |
| `name` | string | `nickname` 的旧版兼容别名；两者同时出现时 `nickname` 优先 |
| `avatar_name` | string | 内置头像名，`[a-z0-9_-]{1,15}`，持久化；不存在则回 `0x1D` 且保留原头像 |
| `token` | number | ≥0（上限 10 亿）。主页 token 进度条的**当前值** |
| `token_max` | number | ≥1（上限 10 亿）。token 进度条的**上限**；**默认 40000**，下发后持久化 |
| `time` | number | **对时**：本地时间的 Unix 秒。设置系统时钟(RTC)后状态栏显示 HH:MM + 星期。**不持久化**，见下 |
| `sleep_min` | number | **无动作息屏分钟数**：静置这么久(无按键/无广播/无连接数据)自动关背光息屏；**0=永不**。默认 5，持久化。任意输入 ≤0.25s 亮屏 |
| `volume` | number | **codec 输出音量** 0..100（超范围自动裁剪）。**当前默认 95**，下发后立即生效并持久化；影响乐谱/提示音/音频片段的播放音量 |
| `game_clear` | bool/number | **清零游戏积分**：`true`/非 0 → 把工牌本地的累计总积分与单局最高**清零**(读走后调用)。动作键，不持久化状态。见「游戏积分同步」 |
| `img_mode` | string | 旧客户端兼容字段；仍可解析/持久化，但 v15 图片上传始终为全屏 JPEG |
| ~~`role`~~ | string | **主页不再显示**（仍被解析并持久化，向后兼容） |
| ~~`subtitle`~~ | string | 同上，不再显示 |
| ~~`battery`~~ | number | 仍被解析持久化，但**不驱动显示**：状态栏电量来自 **CW2017 电量计(真实硬件读数)**，与此键无关 |
| ~~`online`~~ | bool | 仍被解析持久化，但**不驱动显示**：在线点为静态占位(无真实数据源) |
| ~~`level` / `xp` / `xp_max`~~ | number | 同上,不再显示（等级/经验条已移除） |

**`time` 时间同步**

- 值 = **本地墙钟的 Unix 秒**（不是 UTC）。设备把它当作系统时间存入 RTC,状态栏据此显示 HH:MM 与星期。
- 换算公式(含夏令时):
  - JS: `Math.floor(Date.now()/1000) - new Date().getTimezoneOffset()*60`
  - Python: `int(time.time() + time.localtime().tm_gmtoff)`
- **不持久化**:时间是实时值,存 NVS 也会过期;只发 `time` 不会触发 flash 写(避免磨损)。
- **断电/复位会丢时间**(无电池 RTC),需重新对时;**深度休眠不丢**(RTC 继续计时)。
- ⚠️ **精度**:本板 RTC 用内部 RC 振荡器(非 32.768kHz 晶振),会随温度漂移(量级 ~1%),
  长时间不对时会有可见偏差,建议每次连接时对一次。要高精度需硬件加 32k 晶振。

> **主页构成**：顶部状态栏（时间 + 电量图标 + 在线点）+ 头像 + 昵称 + token 进度条（`token/token_max`）+ 底部两格 dock（GAME / IMAGE）。
> - 时间：由 `time` 键驱动（见下）。
> - 电量：**CW2017 电量计真实读数**，5 档图标 + 百分比(≤第 1 档红 / 第 2 档黄 / 其余白)；`battery` 键不参与。未装电量计时显示虚拟占位。
> - `role`/`subtitle`/`level`/`xp`/`xp_max`/`online` 这些键**仍可下发**（不报错、照常持久化），但**不再显示**。
> `avatar_seed` 已在 v6 移除（不再有生成头像），发送会被当未知键忽略。

**游戏积分同步（读特征 …0013 + `game_clear`）**

工牌本地记录小游戏的**累计总积分**（每局累加）与**单局最高积分**，掉电保留、持续累计**直到被同步取走并清零**。因数据不实时同步，采用"**读 → 清空**"批量交接：

1. **读**：读只读特征 `…0013`，返回定长 **9 字节**（小端）：

   | 偏移 | 内容 |
   |---|---|
   | `[0]` | ver = `0x01` |
   | `[1..4]` | 累计总积分 game_total（u32 小端） |
   | `[5..8]` | 单局最高积分 game_best（u32 小端） |

2. **记录**：小程序把这两个值记下（上报服务器用）。
3. **清空**：下发 `{"game_clear": true}` → 工牌把 game_total / game_best **清零**，`…0013` 立即变为全 0，下一周期从 0 重新累计。

> ⚠️ 顺序必须"**先读后清**"：清零不可逆。读失败就别清。
> ⚠️ 清零与"某局刚结束"之间存在极小竞态（清掉了尚未读到的最新一局分），概率极低可接受。
> 备注：门槛/互动规则（单局最高≥阈值给 1 次机会等）在服务器/小程序侧判定，工牌只负责记录与清零。

**内置头像**

设备从 1MB `imgava` 分区的 AVA1 资源包按名称读取 PNG，开机恢复已保存名称。头像
目录不是固定清单：构建时按文件名排序扫描 `assets/avatars/*.png`，当前有几张就打包
几张；1MB 分区按规定头像规格至少可容纳 10 张，实际数量上限由总容量决定。

资源由 `assets/avatars/*.png` 在构建时规范化并打包为 `build/imgava.bin`；普通 `idf.py flash`
以及发布脚本生成的合并固件都会把它写入分区，并生成/携带 `avatar_catalog.json`。客户端
可用该清单展示名称，也可手工发送合法名称；不得上传头像文件。

小程序必须只发送发布包 `avatar_catalog.json` 中存在的 `avatar_name`。名称格式合法但设备
资源包中不存在时，设备返回 `[01][1D]`，当前头像及已保存名称均保持不变；其它合法字段
仍按部分更新规则处理。

- 类型不匹配的键被跳过，不影响其它键；数值超范围自动裁剪。
- 字符串超长**按 UTF-8 字符边界截断**（不会把汉字切成半个）。
- **中文显示**：卡片内置 GB2312 一级汉字（3755 常用字）+ ASCII；**超出字库的生僻字显示为方块**；过长的行显示省略号。

示例：
```json
{"nickname":"小舟","avatar_name":"neon_cat","token":86,"token_max":40000}
```

## 6. 图片（type=0x02；仅全屏基线 JPEG）

图片始终写入 `imgstore`，上传完成后立即全屏显示并常驻；`img_mode` 不再改变目标。
头像选择见 §5 的 `avatar_name`，不使用本通道。

**全屏图的退出方式：长按卡片的确定键约 2 秒。**（这块板的三个按键共用一路 ADC 分压，
物理上无法检测组合键，所以是长按而不是组合键。）退出后回到主界面，并按当前 `avatar_name` 重新显示内置头像。

### ⚠️ 一次只能发一张，必须等上一张出终结状态

**发下一张图之前，必须先收到上一张的终结状态**（`0x01` DONE，或 `0x17/0x19/0x1A/0x1B` 任一失败）。

原因不只是流程规范：图片收齐后设备要花几百毫秒解码，解码期间它正在读 flash 里那份数据。
此时若新的 `BEGIN` 到达，设备为了给新图腾地方会**擦掉同一块 flash**，等于把解码器脚下的数据
抽走。设备侧已经加了保护——这种情况会回 **`0x1B` 设备忙**并拒收，**等 1 秒重发即可**。

但请不要依赖这个保护来做流控：收到 `0x1B` 说明发送节奏本身有问题。正确做法是串行发送：

```javascript
// ✅ 等终结状态再发下一张
await sendImage(imgA)      // 内部 resolve 于收到 0x01 / 0x17 / 0x19 / 0x1A
await sendImage(imgB)

// ❌ 不要这样 —— 第二张的 BEGIN 会撞上第一张的解码
sendImage(imgA); sendImage(imgB)
```

### ⚠️ JPEG 必须是基线，不能是渐进式


设备的硬件解码器**只支持基线（baseline）JPEG**。发渐进式图会回 **`0x19`**。

这不是能通过升级固件解决的：渐进式 JPEG 要求把整幅图的 DCT 系数全部驻留内存直到所有扫描
结束，一张 208×288 的图就需要约 **175KB**，而 ESP32-C3 运行时只有约 **28KB** 空闲堆且无 PSRAM，
差一个数量级。**任何解码库都绕不开这个，因为这是 JPEG 格式本身的性质。**

**手机相册、社交软件保存的图很多都是渐进式的，直接读原文件字节发送几乎必然踩坑。**
正确做法是重新编码一遍——反正为了满足下面的尺寸约束本来就要重编：

```javascript
// 小程序:不要直接读原文件,先压缩/重绘导出,得到的都是基线 JPEG
wx.compressImage({ src: tempFilePath, quality: 85, success(res) { /* 用 res.tempFilePath */ } })
// 或走 canvas 重绘导出,顺便缩到 ≤240×320
```

自查方法（Python）：`Image.open('x.jpg').info.get('progressive', 0)`，输出 `1` 就是渐进式。
或直接看字节：文件里出现 `FF C2`（SOF2）= 渐进式，`FF C0`（SOF0）= 基线。

**图片约束（务必在小程序端处理好，否则回 `0x17` 解码失败）**
- 格式 **JPG**；尺寸 **≤240×320** 且**宽高都是 8 的整数倍**；压缩后 **≤124KB**。

**分片子协议（payload 内部）**
```
BEGIN:  [0x00][total_len(4字节,小端)]    // JPG 总字节数
DATA:   [0x01][chunk...]                 // 建议 ≤220 字节
END:    [0x02]
```
```
BEGIN(total=3315): 01 02 05 00  00 F3 0C 00 00
DATA ("abc"):      01 02 04 00  01 61 62 63
END:               01 02 01 00  02
```

## 7. 乐谱（type=0x03，RTTTL）

RTTTL 文本，卡片用 8bit 方波播放一遍，**≤1024 字节**，不持久化。

> ⚠️ **v4 起上限由 4096 收紧到 1024 字节**（设备侧 RAM 吃紧所致）。超长会在 BEGIN 阶段就回 `0x15` 超长并中止，**请在小程序端先校验 `TextEncoder().encode(rtttl).length <= 1024` 再发**。1024 字节约可容纳 200~300 个音符，常见曲目够用。

```
名字:d=默认时值,o=默认八度,b=BPM:音符,音符,...
音符 = [时值]音名[#][八度][.]      p=休止
```

**分片子协议（注意 total_len 是 2 字节，与图片不同）**
```
BEGIN:  [0x00][total_len(2字节,小端)]
DATA:   [0x01][chunk...]
END:    [0x02]
```
```
BEGIN(total=50): 01 03 03 00  00 32 00
DATA ("abc"):    01 03 04 00  01 61 62 63
END:             01 03 01 00  02
```

## 8. 小程序对接骨架

```js
const SVC   = '54524145-4341-5244-0000-000000000000';
const CMD   = '54524145-4341-5244-0000-000000000010';
const NOTIF = '54524145-4341-5244-0000-000000000011';
let deviceId, mtu = 0;

// ---- 连接：先注册全局通知回调，再订阅 ----
async function connect(d) {
  deviceId = d.deviceId;
  await wx.createBLEConnection({ deviceId });
  try { mtu = (await wx.setBLEMTU({ deviceId, mtu: 247 })).mtu; } catch (e) {}
  await wx.getBLEDeviceServices({ deviceId });
  await wx.getBLEDeviceCharacteristics({ deviceId, serviceId: SVC });

  wx.onBLECharacteristicValueChange(res => {   // ① 全局回调，务必先注册
    const b = new Uint8Array(res.value);
    if (b.length >= 2) handleNotify(b[0], b[1]);
  });
  await wx.notifyBLECharacteristicValueChange({  // ② 再订阅
    deviceId, serviceId: SVC, characteristicId: NOTIF, state: true });
}

// ---- 用 Promise 等待"终结性回应" ----
let pending = null;   // { type, resolve, reject, timer }

function handleNotify(type, status) {
  console.log('notify', type.toString(16), status.toString(16));
  if (status === 0x00) return;              // ACK：进行中，继续等
  if (!pending) return;
  // 帧层错误(type=0x00)也算当前动作失败
  if (type !== pending.type && type !== 0x00) return;
  clearTimeout(pending.timer);
  const p = pending; pending = null;
  if (status === 0x01) p.resolve();
  else p.reject(new Error(STATUS_TEXT[status] || ('错误 0x' + status.toString(16))));
}

function waitDone(type, timeoutMs = 15000) {
  return new Promise((resolve, reject) => {
    pending = { type, resolve, reject,
      timer: setTimeout(() => { pending = null; reject(new Error('设备无响应')); }, timeoutMs) };
  });
}

const STATUS_TEXT = {
  0x10: '帧格式错', 0x11: '传输超时', 0x12: '时序错', 0x13: '内容解析失败',
  0x14: '没有有效字段', 0x15: '数据过长', 0x16: '设备存储失败',
  0x17: '图片解码失败(检查尺寸:≤240×320且宽高为8的倍数)', 0x18: '设备不支持该操作',
  0x19: '图片格式不支持:设备只能显示基线JPEG,请重新编码后再发(见下)', 0x1A: '图片数据不完整,可能传输中断,请重试',
  0x1B: '设备忙,显示正在处理图片或截图,请稍后重试',
};

// ---- 三个业务动作：发完直接 await 结果 ----
async function sendConfig(obj) {
  const p = waitDone(0x01);
  await writeFrame(0x01, new TextEncoder().encode(JSON.stringify(obj)));
  return p;                       // 成功 resolve，失败 reject(带原因)
}

async function sendImage(jpg /* Uint8Array */) {
  const p = waitDone(0x02, 30000);            // 图片要等解码，超时给足
  const begin = new Uint8Array(5); begin[0] = 0x00;
  new DataView(begin.buffer).setUint32(1, jpg.length, true);
  await writeFrame(0x02, begin);
  for (let off = 0; off < jpg.length; off += 220) {
    const s = jpg.slice(off, off + 220);
    const d = new Uint8Array(1 + s.length); d[0] = 0x01; d.set(s, 1);
    await writeFrame(0x02, d);
  }
  await writeFrame(0x02, new Uint8Array([0x02]));
  return p;                       // 等到 DONE 才算图真的显示出来了
}

async function sendScore(rtttl) {
  const bytes = new TextEncoder().encode(rtttl);
  if (bytes.length > 1024) throw new Error('乐谱过长(' + bytes.length + '字节),上限 1024');
  const p = waitDone(0x03);
  const begin = new Uint8Array(3); begin[0] = 0x00;
  new DataView(begin.buffer).setUint16(1, bytes.length, true);
  await writeFrame(0x03, begin);
  for (let off = 0; off < bytes.length; off += 220) {
    const s = bytes.slice(off, off + 220);
    const d = new Uint8Array(1 + s.length); d[0] = 0x01; d.set(s, 1);
    await writeFrame(0x03, d);
  }
  await writeFrame(0x03, new Uint8Array([0x02]));
  return p;
}

// ---- 切换固件内置头像；图片上传通道始终是全屏 JPEG ----
const setAvatar = name => sendConfig({ avatar_name: name });

function writeChar(bytes) {
  return wx.writeBLECharacteristicValue({
    deviceId, serviceId: SVC, characteristicId: CMD, value: bytes.buffer });
}
```

## 9. 约束速查

| 项 | 约束 |
|---|---|
| 设备名 | 本机 SN（通常为 12 位小写十六进制）；按主服务 UUID发现设备，不要依赖固定名称 `TRAE-CARD` |
| 写操作 | 全走命令特征 `…0010`，串行、带响应 |
| 通知 | 必须订阅 `…0011` 的 CCCD；格式 `[type][status]` |
| 帧头 | `[0x01][type][len 小端2字节]`，payload ≤256 |
| 分包 | 单次 ≤ MTU-3；**一帧须 2 秒内写完**，否则回 `0x11` 超时 |
| 终结判定 | `status==0x00` 进行中；`0x01` 成功；`0x1X` 失败 |
| 全屏图 | 基线 JPG，≤240×320，**宽高均 8 的倍数**，≤124KB；终结在解码后(约 1~2 秒) |
| 头像 | `avatar_name` 选择固件内置 PNG；不再上传头像文件 |
| 图片 | `type=0x02` 仅全屏基线 JPEG（常驻，长按确定键退出） |
| 乐谱 | RTTTL，**≤1024 字节**；END 校验成功后持久化并立即播放一次，下次开机再播放一次 |
| 屏幕截图 | `type=0x06` 控制 + `…0014` 数据 Notify；240×320 RGB565-LE，153,600B，通常 15–40 秒；见 §11 |
| JSON | UTF-8，部分更新；nickname/name=47 字节，avatar_name=1..15 ASCII 字符 |
| 字节序 | 帧 len、图片(4B)/乐谱(2B) 的 total_len 均**小端** |
| 中文 | UTF-8（3 字节/字）；内置 GB2312 一级字库，生僻字显示方块 |

## 10. RTTTL 开机音乐持久化

小程序通过 `type=0x03` 下发合法 RTTTL 后，卡片先写入 NVS，再立即播放一次。后续成功下发会覆盖上一首。
设备每次启动时读取并校验该存档：存在且合法则播放一次；不存在、读取失败或内容非法时静默跳过，不使用内置默认曲谱。

## 11. 屏幕截图（type=0x06，v14）

截图是一个**停止等待（stop-and-wait）**传输：控制命令仍写 `…0010`，状态仍由 `…0011` 通知，像素包只由独立 Notify 特征 `…0014` 发出。中央应订阅**两个** Notify CCCD，以接收状态和像素包；固件对 START 的强制前提只有连接仍有效且 `…0014` 已订阅，`…0011` 未订阅不会使 START 被拒绝，但中央将收不到状态。旧客户端只订阅 `…0011` 仍可继续使用 v13 及之前的功能。

### 11.1 控制帧（写 `…0010`）

应用层帧头仍为 `[0x01][0x06][len:u16le]`，其 payload 必须严格等于下表长度。所有多字节字段都是**小端**。

| 操作 | payload | 长度 | 时机 |
|---|---|---:|---|
| START (`0x01`) | `[01]` | 1 | 请求一次当前屏幕截图；设备随后分配非零 `capture_id` |
| ACK (`0x02`) | `[02][capture_id:u16le][seq:u16le]` | 5 | 对 `…0014` 上收到的每一个 META / DATA / END 立即确认 |
| FINISH (`0x03`) | `[03][capture_id:u16le]` | 3 | 已 ACK END 且已保存/处理最终画布后，清理该次完成记录 |
| CANCEL (`0x04`) | `[04][capture_id:u16le]` | 3 | 放弃活动截图或已完成但尚未 FINISH 的截图 |

`capture_id` 由设备滚动生成，`0` 保留不用；`seq` 是 `u16`，从 META 的 `0` 开始，按模 65536 递增。因此 `65535` 的下一包 `seq` 是 `0`。ACK 必须同时匹配当前 `capture_id` 和 `seq`；已解析控制命令的错 ID 或错序号回状态 `0x12`。控制 payload 长度不对或操作码未知都会被解析器作为帧格式错误，回 `0x10`。

### 11.2 像素通知（读 `…0014`）

以下是 **Notify payload 本身**，不再包一层应用帧。所有 `u16` / `u32` 均为小端。

| 包 | 二进制布局 | 固定长度 | 说明 |
|---|---|---:|---|
| META (`0x01`) | `[01][capture_id:u16][seq:u16][width:u16][height:u16][format:u8][total_len:u32]` | 14 | 第一包；`seq=0`，参数固定为 `240`、`320`、`format=0x01`、`total_len=153600` |
| DATA (`0x02`) | `[02][capture_id:u16][seq:u16][x:u16][y:u16][w:u16][h:u16][region_offset:u32][rgb565_bytes…]` | 17 + 偶数字节 | 一个矩形区域的连续部分；`region_offset` 是该区域内的**字节**偏移，数据长度必须为偶数 |
| END (`0x03`) | `[03][capture_id:u16][seq:u16][packet_count:u16][total_len:u32][crc32:u32]` | 15 | 全部 DATA 后；`packet_count` 为 DATA Notify 数量的 `u16` 低 16 位 |

图像画布固定为 `240 × 320` 像素、逐行（x 从左到右、y 从上到下）排列的 RGB565 little-endian。每个像素 2 字节，数值为 `rrrrrggggggbbbbb`，线上字节顺序为低字节、再高字节；即 red 在位 15..11、green 在位 10..5、blue 在位 4..0。接收端按 `(x,y,w,h,region_offset)` 放回最终画布，不能旋转或镜像。

`crc32` 是对该最终完整画布的原始 153,600 字节、按上述逐行 RGB565-LE 顺序计算的标准 IEEE CRC-32（与 `zlib.crc32` 相同）。DATA 的到达包序不改变 CRC 所定义的字节顺序；必须在完整覆盖所有像素、总长度和 DATA 包计数均匹配后才接受 END。`packet_count` 和 `seq` 都按 `u16` 回绕比较。

### 11.3 时序、重传与状态

1. 中央订阅 `…0011` 与 `…0014`，写 START。`…0011` 是接收状态的客户端必要步骤；设备实际只检查连接和 `…0014` 的订阅状态。
2. 设备接受 START 后在 `…0011` 通知 `[06][00]`（ACK，进行中），先发 META；中央为 META ACK。
3. 设备强制重绘并逐包发 DATA；中央**每一包**都用匹配的 ACK 回复。设备在收到 ACK 前不会推进到下一包。
4. DATA 完成后设备发 END；中央校验全画布和 CRC，仍须先 ACK END。设备再通知 `[06][01]`（DONE）。中央可保存 JPG，然后写 FINISH；匹配的 FINISH 会得到 `[06][01]` 并清除五分钟完成记录。

每个已发出的 META / DATA / END 等 ACK **3 秒**。超时后设备最多重发同一缓存包 **3 次**（字节内容、`capture_id` 和 `seq` 不变）；仍未收到匹配 ACK 则以 `[06][11]` 终结并恢复显示交互。中央收到重复包应重新发送其前一次 ACK，且不得重复写入画布数据。实际耗时取决于协商 MTU、连接间隔和手机写时延，完整 153,600B 截图预计约 **15–40 秒**。

START 在截图正在进行、开始已排队、JPEG 上传/解码中或显示捕获资源不可用时回 `[06][1B]`（busy）；固件在连接无效、`…0014` 未订阅或截图通知投递失败时回 `[06][1C]`（not-ready）。`…0011` 的订阅不会被用作 START 准入条件，但中央必须订阅它才看得到这些状态。这两种状态均是终结：修复 `…0014` 订阅/连接或等待忙碌操作结束后，重新 START。

取消可在任一阶段发生，但必须携带当前 `capture_id`。活动截图的匹配 CANCEL 会唤醒 ACK 等待、停止重绘/传输、恢复原先导航和输入，并通知 `[06][01]`；断连则取消而不向已断开的中央补发状态。END 已确认后，FINISH 或同 ID 的 CANCEL 只清理完成记录并回 `[06][01]`，不会再次触碰显示。错误控制 ID/序号不取消其他截图，回 `[06][12]`。

### 11.4 向后兼容

v14 没有改变既有应用帧头、`…0010` 命令写、`…0011` 状态通知、配置、图片、乐谱或音频片段的布局。旧客户端可忽略 `type=0x06` 和新特征 `…0014`；v14 客户端也应按旧规则把 `…0011` 的非 `0x00` 状态视作终结。
